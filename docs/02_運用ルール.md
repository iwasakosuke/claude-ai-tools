# 運用ルール(命名・保存・安全・改善)

全Skill・全作業に共通のルール。Skillより優先される。

---

## 1. 安全ルール(絶対ルール)

AIは以下を**勝手に実行しない**。必ず内容を提示して人間の承認を得る。

| 禁止(承認必須) | 理由 |
|---|---|
| メールの送信 | ドラフト作成まで。送信は人間がGmail上で行う |
| SNS・ブログ等への公開・投稿 | 下書きと投稿文の作成まで |
| 外部サービスへのデータ送信・共有設定の変更 | 情報漏えい防止 |
| 課金が発生する操作(API購入・広告・有料エクスポート等) | 予算は人間が管理 |
| 既存ファイルの上書き・削除(Drive / Notion / リポジトリの成果物) | 新規ファイル or 新バージョンとして保存し、差し替えは人間が判断 |
| 認証情報(パスワード・APIキー・トークン)の閲覧・保存・出力 | リポジトリやチャットに残さない |

**【仮説】** 上記が「事故が起きると困る操作」のはず。実際の禁止領域(特定の顧客フォルダ等)があれば、この表に追記すること。

## 2. ファイル命名規則

```
YYYYMMDD_種別_案件名_v番号.拡張子
例: 20260703_提案書_ABC商事_v1.md
    20260703_議事録_定例MTG_v1.md
    20260710_週報_v1.md
```

- 種別は固定語彙: `提案書` `議事録` `週報` `リサーチ` `メール` `SNS` `デザイン指示` `スクリプト`
- 修正したら v2, v3 と上げる。**旧版は消さない**(上書き禁止ルールと連動)
- 確定版はファイル名末尾に `_final` を付けてよい。final は1案件に1つだけ

## 3. 保存ルール

| 成果物 | 保存先 | 備考 |
|---|---|---|
| ドラフト・作業中 | このリポジトリの `work/`(git管理外にしたければ .gitignore に追加) | まずここに置く |
| 確定した文書 | Google Drive **【仮説】** | 実際の運用フォルダが決まったらパスをここに書く |
| ナレッジ・議事録の蓄積 | Notion **【仮説】** | 保存先ページが決まったらURLをここに書く |
| コード・スクリプト | GitHub(このリポジトリ or 専用リポジトリ) | main直pushはしない。ブランチ→PR |
| テンプレ・Skill・ルール | このリポジトリ | 業務資産の本体。変更はコミットで履歴を残す |

## 4. 品質ゲート(QG)

成果物は提出・送信・公開の前に、必ず対応するチェックリストを通す:

- 文章系(メール・議事録・報告書)→ `checklists/qa-文章.md`
- 提案書・プレゼン → `checklists/qa-提案書.md`
- デザイン・SNS → `checklists/qa-デザイン.md`
- コード → `checklists/qa-コード.md`

AIが成果物を作るときは、**チェックリストを自分で通した結果を成果物に添えて**提出する。人間はチェック済み項目を信頼しつつ、★印(人間判断)の項目だけ見ればよい。

## 5. Skill改善サイクル(資産を育てるルール)

1. Skillの出力を手で直したら、「何を直したか」を一言メモする(直したファイルの末尾でよい)
2. 週1回 `asset-review` Skillを実行 → 直しの傾向をSkill/テンプレに反映
3. 変更はコミットメッセージに `improve: <skill名> <変更理由>` で記録
4. うまくいかないSkillは捨ててよい。**使われないSkillは資産ではなく負債**

## 6. AIへの依頼のしかた(判断コストを下げる型)

毎回ゼロから指示を考えない。以下の3点だけ渡せばSkillが動く:

```
1. 何を作るか(種別)     例: 「ABC商事向けの提案書」
2. 材料(あるものだけ)   例: 議事メモ、前回資料、URL
3. 締切と重要度           例: 「明日提出。トーンは堅め」
```

迷ったら「○○を作りたい。材料はこれ。どのSkillを使うべき?」と聞けば、AIが選ぶ。
