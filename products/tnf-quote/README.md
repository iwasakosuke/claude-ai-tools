# TNF Quote — 見積 → 請求 → 入金 SaaS(Base44)

Web制作会社・フリーランス・デザイナー向け。設計書(`docs/TNF_Quote設計書v2`)を Base44 前提で
React + TypeScript 実装したもの。**保守性最優先**で、プラットフォーム(Base44)に依存しない
「業務ロジックの核」を独立させ、テストで守っている。

---

## いちばん大事な設計方針:3層に分ける

```
src/
├── domain/   ← プラットフォーム非依存の純粋ロジック(金額・税・源泉・採番・状態遷移・権限)
│              　単体テスト済み。Base44 も React も知らない。
├── server/   ← バックエンド関数(createQuote 等)。domain を呼び、Repo 経由で保存。
│              　Repo は「ポート」= 抽象。本番=Base44 / テスト=インメモリ を差し替え。
└── web/      ← React コンポーネント。domain の recalcTotals で画面合計を出す
               　→ 画面の数字とサーバー確定値が絶対にズレない。
```

なぜこう分けるか: 請求SaaSの生命線は**金額計算の正しさ**。ここが Base44 SDK や React に
絡むと、テストできず壊れやすくなる。だから計算は素の関数に閉じ込め、`node --test` で常に検証する。

```bash
npm install

```

> テストは Node 22 の型ストリップ + 標準テストランナーで動く(追加ランタイム不要)。

### いま通っているテスト(32件)
- 消費税の税率別・切り捨て、値引きの按分(残差ゼロ)
- **源泉徴収**: 10.21% / 100万円超 20.42%、境界値、税抜・値引き後を課税標準に
- 見積↔請求の**別採番**、状態遷移(draft→sent→accepted…)
- **着手金 + 残金 = 元見積**(分割しても金額が一致)
- 一部入金は `paid` にせず残額を返す/完済で `paid`
- 権限マトリクス(owner/admin/member/viewer、member は自分の担当分のみ)
- Free プランの月次上限

## 金額まわりの設計判断(仕様が沈黙している箇所)

コードのコメントにも明記しているが、要点:

- **丸め**: 明細金額=四捨五入、消費税=税率ごとに1回切り捨て(適格請求書の要件)、源泉=切り捨て。
- **源泉の課税標準**: 消費税を区分表示するため**税抜(本体)・値引き後**を対象にする(国税庁の取扱い)。
  実費立替など対象外の品目は `withholding_eligible=false`(明細/プリセットで制御)。
- **分割請求**: 各明細の金額を比率で分割し、`残金 = 全額 − 着手金`で一致を保証。
  税・源泉は請求書ごとに1回丸めるため、全額1枚と着手金+残金2枚で税額が最大1円ずれ得るが、
  各請求書はそれぞれ正しく丸められた独立の適格請求書。

> 上記の丸め・課税標準の扱いは一般的な実務に基づく**設計判断**です。実運用前に顧問税理士の確認を推奨します(特に源泉の対象品目・課税標準)。

## Base44 への配線メモ

- `entities/*.json` … Base44 のエンティティ定義。`id/created_date/updated_date/created_by` は自動付与前提。全エンティティに `org_id`(テナント分離)。
- バックエンド関数 … `src/server/functions/*` を各 Base44 function から import し、`createBase44Repo(client)` で作った Repo と入力を渡すだけ。**業務ロジックは書き換えない**。
- **採番の原子性** … `quote_seq/invoice_seq` の +1 は競合で番号重複が起きうる。Base44 の条件付き更新か採番専用 function で楽観ロックにし、結合テストで重複ゼロを確認すること(`base44Repository.ts` に注意書きあり)。
- 全クエリを `org_id` で強制し、金額・番号・ステータスはサーバー確定(フロントの値を信用しない)。
